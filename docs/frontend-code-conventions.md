# 前端代码组织与分层规范

本文件记录仓库约定的代码规则和开发习惯，供开发、代码审查和后续重构参考。核心原则是关注点分离、单一职责、模块化和避免重复（DRY），目标是让业务逻辑容易定位、复用和维护。

适用于 Creator Portal、CN Portal、Admin 和 Design Engine 的新增或修改代码。遵循各模块已有的合理结构，逐步改善实际涉及的代码；本规范不代表所有历史代码已经符合要求，也不要求为了统一目录或减少行数进行整体重构。

## 1. 页面负责入口和组装

`src/app/**/page.tsx` 主要处理路由参数、服务端认证、调用查询层和组装页面组件。业务模型、复杂交互、大块可独立维护的 UI 放到对应模块。

服务端页面可以直接调用查询函数，不必为每次查询再增加内部 HTTP API，也不要拼接应用自己的域名请求自己的 API。

简单页面可以保留少量直接展示的 JSX。是否拆分取决于职责、重复和复杂度，不设固定行数限制。

```tsx
import { notFound } from 'next/navigation';
import OrderDetail from '@/components/orders/OrderDetail';
import { getOrderById } from '@/lib/queries/orders';
import type { OrderDetailPageProps } from '@/lib/types/order';

export default async function OrderDetailPage({ params }: OrderDetailPageProps) {
  const { id } = await params;
  const order = await getOrderById(id);
  if (!order) notFound();
  return <OrderDetail order={order} />;
}
```

## 2. 组件按业务组织，按职责复用

展示组件放在 `components/<业务域>`。一个业务域包含多个流程时，再按 `list`、`editor`、`create`、`import`、`sync` 等职责分组，避免把所有文件堆在路由目录或一个平铺的 components 目录。

- 列表先定义有明确职责的条目组件，例如 `OrderCard`、`ProductRow`，由列表组件组合使用。
- 实际跨业务使用的空态、缩略图、弹窗等放到 `components/ui`。
- 相同业务行为抽取共同实现，例如创建和重新编辑共用编辑器会话；不要复制两份保存、加载或校验逻辑。
- 只有单一使用场景的小块 JSX 可以保留在所属组件。拆出的组件应有清楚的职责，避免产生大量仅转发 props 的空壳。
- 不同 app 的 UI 各自维护。界面相似不等于业务相同，不强制跨 app 共用表现层。

## 3. 状态放在合适的层级

`useState`、自定义 hook 和 store 解决的是不同范围的问题，不要求所有状态都用同一种方式。

| 状态或行为 | 放置位置 | 示例 |
| --- | --- | --- |
| 单组件的展示状态 | 组件内 `useState` | 弹窗开关、当前展开项 |
| 一个业务流程的请求、表单和操作状态 | `hooks/<业务域>/useXxx` | 商品编辑、订单同步、导入保存 |
| 多个独立组件共同维护的客户端状态 | 对应业务 store | 设计文档、画布选择、当前产品 |
| 分享或刷新后需要保留的筛选条件 | URL 参数及对应 hook | 搜索、排序、分页 |
| 服务端读取的数据 | 查询结果和 props | 订单详情、商品列表 |

增删改、校验、pending 和错误处理属于业务流程时，应由对应 hook 或 store action 提供统一入口。组件调用这些操作并呈现结果，不在多个按钮或页面中重复实现。

不要仅为了缩短组件，把纯计算塞进 hook；纯计算用普通函数。服务端数据也不必另存一份全局 store，避免重复的数据来源。

## 4. 请求、数据访问和业务规则分开

Portal 类应用优先沿用以下职责划分：

| 层级 | 职责 |
| --- | --- |
| `components` | 展示、交互绑定、局部展示状态 |
| `hooks` | 请求编排、业务交互状态、操作反馈 |
| `lib/api` | 浏览器 HTTP 调用、响应解析、错误处理 |
| `lib/queries` | 数据库读取；浏览器查询用 `.client.ts` 明确标识 |
| `lib/<业务域>/mutations.ts` | 数据库写入和相关操作 |
| `lib/<业务域>` 中的纯函数 | 校验、数据转换、payload 构造、价格计算 |
| `app/api` | 服务端认证、输入校验、调用服务并返回响应 |

已有合理的独立服务可以继续沿用，不为满足目录名增加无意义的包装层。

请求失败应进入明确的错误状态，不把失败当成空列表或保存成功。多来源请求允许部分成功时，应给调用方返回可用结果和失败信息。可能重叠的请求要考虑取消或防止旧结果覆盖新状态；重复触发的写操作要有 pending 保护。客户端保护不能代替有需要时的服务端幂等控制。

## 5. 共享业务类型抽出，组件专属 Props 就近定义

- 多处使用的业务模型、API 响应和通信契约放到领域类型文件，直接 import 复用。
- Portal 类应用沿用 `lib/types`；Design Engine 沿用已有 `types`。
- 单个组件自己的 `Props` 放在组件旁边，不集中到一个巨大类型文件。
- hook、store 或算法独有的内部类型可以保留在所属模块。
- 已被多个模块使用、表示实际业务数据的类型，不应由某个 UI 组件充当定义来源。
- ERP 原始数据和跨应用协议优先复用 `packages/shared`；页面展示模型可以单独定义，并通过转换函数生成，避免复制原始契约。

类型导入使用 `import type`。外部响应和存储数据需要运行时校验；`as SomeType` 不能替代校验，也不要为了绕过错误使用 `any` 或多次强制转换。

## 6. 业务逻辑与配置避免随意硬编码

服务地址、部署配置和凭据从对应环境配置读取，并在统一入口解析、校验。URL 构造和参数编码由共同工具处理，避免散落在多个流程。

价格、成本、等级规则等必须有可信来源。未知金额保持为空或缺失，展示“价格暂不可用”等状态；不要用固定金额或 `0` 掩盖缺失。真实的 `0` 要保留，相关回退使用 `??` 并结合有效性校验。

固定 UI 尺寸、动画时间、协议标识和明确的默认值可以作为常量。相同值代表同一个规则且多处使用时再统一提取；不要求把每个数字都改成全局常量。业务常量要有明确依据，不能靠起一个常量名把未知规则变成可信规则。

演示模板、mock 数据和生产业务数据应有清楚的使用边界，生产路径不以演示金额或产品替代真实数据。

## 7. 共享边界保持清楚

跨 app 的 ERP 请求、签名、图片代理、取价和领域契约复用 `packages/shared`。各 app 专属的路由、UI、语言和业务流程留在各 app 内。

服务端能力和浏览器可用能力分开导出。包含 Node.js API、服务端凭据或数据库管理权限的代码不能经公共 barrel 混入客户端；浏览器使用纯类型和纯计算的子路径。

复用的依据是同一个业务含义和行为，而不是两段代码看起来相似。不同权限、定价或流程规则不要勉强合成一个充满条件分支的通用模块。

## 8. Design Engine 保留已有合理分层

Design Engine 已有 `components`、`stores`、`hooks`、`core`、`types` 和 `plugins`，继续沿用其分层，不强制改成 Portal 的目录结构。具体模块约定参考 [Design Engine 开发说明](../design-engine/CLAUDE.md)。

- UI 面板放在 `components/editor`，嵌入配置 UI 放在 `components/embed`。
- 设计、产品和编辑器状态由各自 store 管理；设计操作通过 action 更新。
- 生命周期、模板加载和快捷键等由 hooks 编排。
- 画布、转换、校验、导出等核心能力放在 `core`，保持与 React 组件分离。依赖浏览器或 Fabric.js 的模块不因此自动具备服务端运行能力。
- 外部产品经 converter 转成统一 `ProductTemplate`，核心编辑逻辑使用统一模型。
- 编辑器通过已有配置、回调和通信协议与宿主交互，组件专属 Props 保留在组件文件。

复杂编辑器组件较长不自动构成违规。出现独立的保存流程、重复的数据构造、跨组件业务类型或重复工具操作时，再按职责收敛；不要仅按行数拆文件。

## 9. 命名、导入与修改习惯

组件文件使用 PascalCase，hooks 使用 `useXxx`，store 使用现有 `useXxxStore` 约定，其他工具和类型文件沿用业务域既有命名。组件内事件处理通常使用 `handleXxx`，回调 props 使用 `onXxx`。

优先使用项目配置的 `@/` 别名定位跨目录模块。相邻模块的导入和代码格式遵循所在模块约定；不在一次业务修改中顺带大规模更换格式或目录命名。

新增代码先检查已有组件、hook、服务和类型是否可复用。重构时同步更新调用方并清理已确认无人使用的旧实现。行为变化应单独说明，不把定价、校验或错误处理的变化描述成纯目录整理。

## 10. 审查与验证

审查重点：

- 页面是否混入复杂业务流程或重复的大块 UI？
- 是否复用了已有组件、业务操作和类型？
- 状态、请求、查询、写操作和纯计算是否有清楚的职责？
- 是否编造了缺失数据的默认值，或散落了同一份业务规则和配置？
- 是否为了缩短文件引入无实际职责的拆分或不必要的全局状态？

验证按实际修改范围进行：运行相关类型检查、lint 和必要的构建。业务校验、数据转换和价格规则变化需要有意义的测试；纯移动或展示整理不必增加照搬实现的测试。涉及交互流程时验证成功、失败和重复操作路径，并明确哪些外部集成尚未实际验证。
